Source

Primary purpose

Develop, implement and maintain automated and manual test solutions to ensure electronic products and sub-assemblies are correctly manufactured and perform to specification.

Maintain and improve test fixtures and test methodologies, with the aim of automating testing as much as possible.

Work with Manufacturing Engineering and Engineering to develop and improve test processes and methodologies.

Source

Key responsibilities

  • Design, develop and support functional test solutions, hardware and software, for electronic assemblies and systems.
  • Develop automated test programs using ATE platforms.
  • Write, modify, debug and validate production test software.
  • Configure and integrate electronic instrumentation including oscilloscopes, DMMs, power supplies, electronic loads, spectrum analysers and DAQ systems.
  • Develop and maintain test documentation including plans, SOPs and reports.
  • Analyse production test data for trends, shifts and anomalies across products and manufacturing sites; generate and present summary reports.
  • Work cross-functionally with manufacturing, design, quality and subcontract suppliers to implement corrective actions resulting from data analysis.
  • Review test data and equipment usage statistics to identify preventative strategies and reduce long-term risk.
  • Work with product design teams on DfM and DfT during new product development.
  • Provide technical input into manufacturing/test strategy including capacity planning, supplier process capability and new-supplier evaluation.
  • Act as a technical contact for subcontract electronics manufacturers and support production-test problem solving.
  • Improve test efficiency, coverage, reliability and throughput.
  • Ensure compliance with applicable safety and regulatory standards.
  • Feed back on product testability, coverage, diagnosability, reparability, firmware/diagnostics, user experience, test time and yield.
  • Interpret electrical diagrams and electronic schematics and relate them to the physical product.

What the JD is really asking for

The difficult engineering core is not manufacturing administration. It is an engineer who can move between the DUT, schematic, instruments, test fixture, software and production data; determine whether a failure is real or test-induced; automate the useful parts; and leave behind a repeatable production-capable test solution.

The manufacturing-process items are still real requirements and should not be ignored; they are separated explicitly in the fit notes rather than being treated as equivalent to the technical core.

Measurement / test-method judgement

Examples include:

  • Receiver sensitivity: learned the normal measurement envelope and avoided over-interpreting small (~0.3 dB) shifts within a much wider acceptable specification margin.
  • VNA/test setup: identified one unit/setup drifting further out of calibration, explaining misleading red-herring data.
  • IOBC procedure: recognised that assumptions about noise stability and cross-channel coupling did not reflect real behaviour; literal adherence could cause systematic false failures, implying the procedure itself required revision.
  • Antenna S11: questioned whether secondary lobes in an uncontrolled/non-shielded room were repeatable DUT properties; small orientation changes affected traces enough to challenge their use as hard acceptance criteria. Better terminology is environmental/multipath/fixture-induced structure rather than strict signal-processing “aliasing”.

Technical-question reminders

Python ATE architecture

  • DUT object and instrument/test-equipment objects.
  • Test-case/test-sequence layer separate from drivers.
  • Config/limits externalised via simple config or minimal GUI.
  • Session logging separate from formal result CSV.
  • Timestamped files with station/session/configuration metadata in headers.
  • Clear instrument reset/init and error handling.

I2C NACK debug

Start physical/electrical before blaming software:

  • power and rail integrity;
  • pull-ups and logic levels;
  • scope SDA/SCL for timing/non-standard behaviour;
  • MCU/peripheral reset/state;
  • then firmware timing, transaction sequencing, timeout/recovery logic.

Spectrum analyser setup

RBW, VBW, span, detector, attenuation and sweep time are coupled trade-offs. Choose settings from the signal bandwidth, required noise floor/dynamic range, whether the event is intermittent and required production throughput. Avoid blindly using maximum resolution when it only increases test time.

SCPI over RS-232/Ethernet

Design for:

  • realistic operation-specific timeouts;
  • termination/newline handling;
  • IDN/connection validation;
  • known/reset instrument state;
  • stale buffers/partial responses;
  • operation-complete or status checks where appropriate;
  • reconnect/retry policy with bounded retries;
  • useful communication/error logging.

PCBA cold-pass / warm-fail

  • establish power rails first with DMM/scope;
  • profile relevant test points over time/temperature;
  • trigger on rail dips/noise or fault onset;
  • correlate failure with temperature and component/region where possible;
  • separate DUT thermal drift from fixture/instrument/test-software effects.

Mixed-signal PCBA fault finding

Hierarchy:

  1. external supply/input power;
  2. main rails;
  3. enables/reset/clock/MCU boot;
  4. peripheral power/state;
  5. analogue signal chain;
  6. digital buses such as SPI only once prerequisites are known-good.

High-current voltage droop

  • verify electronic-load settings/limits and cabling first;
  • measure voltage drop along PCB/cable path under load;
  • check whether deltas make sense from R = V/I and P = VI;
  • check current limiting/regulator behaviour and thermal rise;
  • Eaton H-bridge work provides a real high-current anchor, including differential scope probing and loads up to ~10 A.

Oscilloscope for intermittent interface faults

  • trigger on the symptom/event if possible rather than free-run;
  • use suitable probe loading/grounding;
  • enough bandwidth/sample rate to see edge/timing issues, not just protocol-level states;
  • deep memory for pre/post-trigger context;
  • persistence/history/segmented capture for rare events;
  • correlate digital fault with power/reset/enable lines when relevant.

Production fixture design

Direct classic bed-of-nails fixture ownership is not one of the strongest evidenced areas, so do not overclaim. The transferable approach is:

  • use robust connectors/test points where available;
  • choose pogo/bed-of-nails only where volume/access justify it;
  • control cable length, grounding and shielding for analogue/RF signals;
  • minimise contact resistance for power/high-current paths;
  • add fixture self-test/loopback/reference checks where practical;
  • key/interlock connections to reduce operator variability and incorrect mating.

PSU + electronic-load sequencing

  • start in a safe unloaded/current-limited state;
  • initialise instruments and verify known state;
  • apply supply, allow defined settling, verify rails before applying load;
  • ramp/load in controlled steps where appropriate;
  • monitor limits continuously and abort on unexpected voltage/current/temperature;
  • on any exception remove load and power in a safe deterministic order;
  • log the condition causing shutdown rather than simply returning FAIL.
